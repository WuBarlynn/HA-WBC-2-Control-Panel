## 2. 技术栈摘要

- **语言 / 运行时**：Go 1.26+，单二进制 `ha-wbc-console`
- **前端**：内嵌 `web/`（`index.html` + `app.js` + `style.css`），无构建链
- **存储**：本地 JSON 文件（默认 `ha-wbc-data.json`，权限 `0600`，原子写）
- **认证库**：自研 WebAuthn（`internal/webauthn`），管理员密码 PBKDF2-HMAC-SHA256（120000 次迭代）
- **设备通信**：`internal/wbc` 客户端，HTTP（设备固件无 TLS），用设备 WiFi 密码换 `tK`，再 `Authorization: Bearer <tK>` 调设备 API
- **部署形态（本户实测）**：OpenWrt 上跑控制台监听 `localhost:8088`，经 Cloudflare Tunnel 暴露公网 HTTPS

架构（摘自 README，与代码一致）：

```text
浏览器 / 助手
   │  控制台 Bearer 会话（或未来 API Token）
   ▼
Go HTTP Server（控制台）
   ├── 管理员密码 / Passkey
   ├── JSON 文件存储
   └── HA-WBC-2 API Client
          │  设备 Bearer tK
          ▼
      HA-WBC-2 开机卡（局域网 HTTP）
```

## 3. 现有认证流

### 3.1 管理员密码

| 步骤 | 接口 | 说明 |
|------|------|------|
| 首次初始化 | `POST /api/setup` | body `{ "password": "..." }`，≥6 位；成功返回会话 `token` |
| 登录 | `POST /api/login` | body `{ "password": "..." }`；失败故意 sleep ~600ms |
| 改密 | `POST /api/password` | 需已登录；`{ "old", "new" }` |
| 校验 | `store.CheckAdmin` | PBKDF2 常量时间比较 |

密码哈希格式：`pbkdf2:<iter>:<salt_hex>:<key_hex>`，持久化在 `adminHash`。

### 3.2 通行密钥（Passkey / WebAuthn）

| 步骤 | 接口 | 鉴权 |
|------|------|------|
| 注册 begin/finish | `POST /api/passkey/register/begin`、`.../finish` | 需已登录 |
| 登录 begin/finish | `POST /api/passkey/login/begin`、`.../finish` | **公开** |
| 列表 / 删除 | `GET /api/passkey/list`、`DELETE /api/passkey/{id}` | 需已登录 |

- rpID 从请求 `Host` 自动推导（本环境为 `wbc.wubarlynn.top`）
- IP 访问不可用 Passkey；需 localhost 或域名 + HTTPS 安全上下文
- 登录成功同样发放会话 `token`
- 公网实测：`GET /api/state` → `passkeys: 2`，`rpId: "wbc.wubarlynn.top"`，`initialized: true`

### 3.3 会话（Session）

实现：`internal/server/auth.go`

- 32 字节随机 → hex 字符串
- **仅内存** `map[token]expiry`，**进程重启全部失效**
- TTL：**24 小时滑动续期**（每次校验成功刷新）
- 传递方式：`Authorization: Bearer <token>`（前端 `localStorage.wbc_token`）
- 中间件：`Server.authed` → `sessions.valid(bearerToken(r))`

**对助手的含义**：没有长期凭据；无法靠 Passkey（需浏览器/用户在场）；若把管理员密码交给助手长期用，等于共享最高权限且每次登录仍脆弱，且不符合「免用户批准」目标。

### 3.4 设备层令牌（与控制台会话无关）

控制台保存各设备的 WiFi 密码与缓存 `tK`，自行登录设备并代理操作。助手**不应**、也**不必**直接拿设备 WiFi 密码或 `tK`；应只调控制台 API。

## 5. Cloudflare 层结论

| 项 | 结论 |
|----|------|
| 公网域名 | `wbc.wubarlynn.top` |
| DNS | CNAME → `60d2907d-….cfargotunnel.com`，**proxied** |
| Tunnel | 名 `ax3000t`，ingress：`wbc.wubarlynn.top` → `http://localhost:8088` |
| 同隧道另有 | `openwrt.wubarlynn.top` → `http://localhost:80` |
| Cloudflare Access（Zero Trust） | **未**挂在 `wbc.wubarlynn.top`；Access 应用仅见 `openwrt.wubarlynn.top` 等 |
| 实测 | `GET /api/state` 公网 200 且无 Access 登录墙；`GET /api/devices` 无 Bearer 时为**应用层** 401（`未登录或会话已过期`），响应头有 `server: cloudflare` 但无 Access 挑战 |

含义：

1. 今天公网安全完全依赖**控制台自身**的密码 / Passkey / 会话。
2. 给助手加长期凭据，**优先在应用层做 API Token**即可落地，不必先开 Access。
3. 若以后给 `wbc` 也套 Access：浏览器 Passkey 仍可用（用户走 Access 登录）；助手则需 **Access Service Token**（`CF-Access-Client-Id` / `CF-Access-Client-Secret`）**再加**应用层 Token，否则只有边缘通行证、进不了控制台 API。

本机 `~/Projects/blip/deploy/homelab-tunnel` 是另一套「Blip 监控 + Access Service Token」模板，**不是**当前 `wbc` 的运行配置；可作 Access 加固参考，勿与现网混淆。

## 6. 「助手长期自动调用」方案对比

| 方案 | 能否免用户每次批准 | 进程重启后是否仍有效 | 改动成本 | 与现有 Passkey/密码并存 | 风险 / 注意 |
|------|--------------------|----------------------|----------|-------------------------|-------------|
| **A. 应用层 API Token（推荐）** | 是 | 是（写入 JSON） | 中（服务端 + 设置页） | 好：会话与 Token 双轨 | Token 泄漏=可开机；需哈希存储、可吊销、建议 scope |
| B. Cloudflare Access Service Token | 仅过边缘；**现网 wbc 未开 Access** | 是（在 CF 侧） | 低～中（Dashboard） | 需另配 Access 策略，易影响人类登录 | 单独使用**不能**替代应用鉴权；适合作为第二道门 |
| C. HMAC 签名请求 | 是 | 是 | 高 | 可并存 | 防重放要做 timestamp/nonce；助手实现重 |
| D. 长期 session / 拉长 TTL / 持久化 session | 勉强 | 若持久化则是 | 中 | 混淆人类会话与机器人 | 难轮换、难细粒度吊销；重启策略尴尬 |
| E. 助手保存管理员密码反复 `POST /api/login` | 是（自动化角度） | 是 | **零代码** | 滥用最高权限 | **不推荐**：等同共享 root；审计差；登录接口可被刷 |

### 推荐：**A. 应用层 API Token**（可选后续叠加 B）

理由（贴合本仓库现状）：

1. 现有 `authed` 只认内存 session → 机器人天然需要**持久、可吊销、与人类会话分离**的凭据。
2. `wbc` **没有** Access，只上 B 解决不了应用 401。
3. 改动集中、与 Go 现有 Bearer 风格一致，Grok Bot 用 `curl`/`fetch` 即可。
4. 可做 **scope**（如仅 `read` + `power`，禁止 `factory-reset` / 改密 / 管 Passkey）。

## 7. 推荐方案：改动要点（文件级，供接手实现）

> 以下为设计建议，**本分析未改代码**。

### 7.1 数据模型 — `internal/store/store.go`

在 `persisted` 增加例如：

```go
type APIToken struct {
    ID         string    `json:"id"`
    Name       string    `json:"name"`       // 如 "grok-bot"
    Hash       string    `json:"hash"`       // sha256(hex) 或带前缀的哈希，禁止存明文
    Prefix     string    `json:"prefix"`     // 明文前 8 字符，便于识别
    Scopes     []string  `json:"scopes"`     // 如 ["overview","power"]
    CreatedAt  time.Time `json:"createdAt"`
    LastUsedAt time.Time `json:"lastUsedAt,omitzero"`
}
```

- 明文 Token 仅在**创建接口响应里出现一次**（类似 GitHub PAT）。
- 建议格式：`wbc_` + 足够长的随机（≥32 字节）。

### 7.2 鉴权中间件 — `internal/server/server.go`

扩展 `authed` / 新增 `authedWithScope(scope)`：

1. 解析 `Authorization: Bearer …`
2. 若 `sessions.valid(tok)` → 人类会话，**全权限**（保持现状）
3. 否则按 API Token 哈希查找 → 校验 scope → 更新 `LastUsedAt`
4. 可选：同时支持头 `X-Api-Token: …`（方便部分客户端）

### 7.3 管理 API — `internal/server/`（新文件如 `apitoken.go`）

| 方法 | 路径 | 鉴权 | 说明 |
|------|------|------|------|
| POST | `/api/tokens` | 仅**会话**（禁止用 API Token 自造 Token） | 创建，返回明文一次 |
| GET | `/api/tokens` | 会话 | 列表（无明文、无哈希） |
| DELETE | `/api/tokens/{id}` | 会话 | 吊销 |

### 7.4 前端 — `web/app.js` / 设置页

「系统设置」增加 API Token：创建、复制一次、吊销。文案标明给助手/自动化用。

### 7.5 安全注意

- 明文只存助手侧密钥库（Grok Bot 凭据），**永不**写进 git / 群聊 / 本分析文档。
- 建议默认 scope **不含** `factory-reset`、`password`、`passkey-admin`、删设备。
- 控制台日志已对写操作打点；可为 API Token 请求加 `via=api-token name=…` 日志字段。
- 公网仅靠 Token 时，泄漏即远程开机：可后续给 `wbc` 加 Access，助手带 Service Token + API Token。
- 轮换：吊销旧 Token → 发新 → 更新助手配置。

### 7.6 助手侧请求示例（占位符，无真实密钥）

列出设备 / 总览：

```bash
curl -sS 'https://wbc.wubarlynn.top/api/overview' \
  -H 'Authorization: Bearer wbc_REPLACE_WITH_API_TOKEN'
```

开机（将 `DEVICE_ID` 换成 `GET /api/devices` 返回的 id；body 字段以实现时 `opPower` 为准，当前为 JSON `state` 布尔）：

```bash
curl -sS -X POST 'https://wbc.wubarlynn.top/api/devices/DEVICE_ID/power' \
  -H 'Authorization: Bearer wbc_REPLACE_WITH_API_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{"state":true}'
```

关机：`"state":false`。

若将来启用 Cloudflare Access（当前未启用）：

```bash
curl -sS 'https://wbc.wubarlynn.top/api/overview' \
  -H 'Authorization: Bearer wbc_REPLACE_WITH_API_TOKEN' \
  -H 'CF-Access-Client-Id: REPLACE_CF_CLIENT_ID' \
  -H 'CF-Access-Client-Secret: REPLACE_CF_CLIENT_SECRET'
```

## 8. 验收建议（实现后）

1. 密码 / Passkey 登录与现网行为不变。  
2. 用 API Token 可调 `overview` / `power`；无 Token / 错 Token → 401。  
3. 进程重启后 Token 仍有效；session 仍会丢（符合现设计）。  
4. 吊销后立即 401。  
5. 窄 scope 的 Token 调 `factory-reset` → 403。  
6. 创建接口返回的明文无法再从 list 读出。  
7. 不把 Token 写入仓库或聊天记录。

## 9. 结论一句话

**在控制台增加可吊销的应用层 API Token（Bearer），让 Grok Bot 长期调用 `https://wbc.wubarlynn.top`；Cloudflare 当前仅 Tunnel、无 Access，可作后续加固。禁止用管理员密码或 Passkey 充当机器人凭据。**
